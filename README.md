# shellagotchi

A Linux userland "terminal pet" daemon. Your virtual pet lives in a small
Unix-socket daemon and is fed by the exit codes of the shell commands you
run: a clean exit (`0`) is a good meal, everything else is a risky one.
Check on it from the CLI, watch it live in a `ratatui` TUI, or see a
one-line summary baked into your shell prompt.

## Quickstart

```bash
git clone <this-repo> && cd shellagotchi
cargo build --release
```

Start the daemon. If you have a systemd user session, let `install` set up
and enable a user unit for you:

```bash
./target/release/shellagotchi install
```

`install` writes `~/.config/systemd/user/shellagotchi.service` and, if a
systemd user session is detected, runs `systemctl --user daemon-reload &&
systemctl --user enable --now shellagotchi.service`. If no systemd user
session is available (containers, minimal VMs, etc.), it just writes the
unit file and tells you so; in that case start the daemon directly instead:

```bash
./target/release/shellagotchi daemon &
```

Then wire up your shell so every command you run feeds the pet, and add a
`shellagotchi prompt` call to your prompt:

```bash
# bash: append to ~/.bashrc
eval "$(shellagotchi init bash)"

# zsh: append to ~/.zshrc
eval "$(shellagotchi init zsh)"

# fish: append to ~/.config/fish/config.fish
shellagotchi init fish | source
```

Restart your shell (or `source ~/.bashrc` etc.) and you're live. Check in
any time with:

```bash
shellagotchi status     # bordered ASCII status card (or `shellagotchi show`)
shellagotchi watch       # live-updating TUI (q=quit, c=clean, p=pet, r=refresh)
```

Run `shellagotchi doctor` any time something seems off — it checks config,
socket, daemon connectivity, prompt cache freshness, and rc-file hook
presence, and prints a pass/fail report.

## What it does

- **Good/bad food**: every command's exit code is reported to the daemon
  via the shell hook. A `0` exit is a healthy meal (raises satiety); a
  non-zero exit is junk food (raises `bad_food_meter`, which slowly decays
  back down over time). Certain risky commands (`rm`, `kill`, `pkill`,
  `dd` by default, configurable) always count as junk food regardless of
  their exit code.
- **Sleep**: the pet has a configured nightly sleep window
  (`sleep_start_hour`..`wake_hour`); energy drains while awake and
  recovers while asleep.
- **Boredom**: if too much real time passes with no commands fed to it
  (`boredom_after_minutes`), boredom rises.
- **Pooping**: NOT time-based — the pet poops once every
  `poop_interval_commands` commands it's fed, tracked as a running command
  counter. Poops lower hygiene until cleaned. Running a command whose
  argv0 is in `clean_commands` (default: `clean`, `shellagotchi-clean`)
  automatically clears poops and maxes hygiene — no extra setup needed
  beyond the normal shell hook, though `shellagotchi init --with-clean-alias`
  can also wrap an explicit `clean()` shell function for bash/zsh.
- **Sickness**: sustained poor hygiene/satiety can push the pet into a
  `Sick` activity state; it recovers automatically once hygiene and
  satiety both recover past healthy thresholds.
- **Death**: if health reaches 0, the pet's activity becomes `Dead`. See
  the FAQ below — reviving a dead pet is not yet implemented.
- Offline catch-up: while the daemon isn't running (laptop suspended,
  daemon crashed, etc.), the next tick simulates the elapsed real time,
  capped at `max_offline_hours` (default 12h) so a multi-day gap doesn't
  instantly and unrealistically tank every stat.

## CLI reference

Generated by hand from `src/main.rs`'s `clap` definitions — kept in sync
with the real subcommand list (also available as `man shellagotchi`, see
below).

| Command | Flags | Description |
|---|---|---|
| `shellagotchi feed` | `--exit <i32>` (required), `--duration <u64>` (ms, default `0`) | Reports a command's exit status to the daemon. Called from the shell hook after every command; always exits `0` and prints nothing, even if the daemon is unreachable. Reads `SHELLAGOTCHI_ARGV0` from the environment (set by the shell hook) to detect junk-food/clean commands. Short-circuits with no I/O at all if `SHELLAGOTCHI_DISABLE` is set (see FAQ). |
| `shellagotchi daemon` | — | Runs the daemon: binds the Unix socket, serves IPC requests, ticks the pet forward on a timer, persists state. Foreground process (run it under systemd via `install`, or backgrounded manually). |
| `shellagotchi prompt` | `--format <compact\|minimal\|verbose>` (default `compact`) | Prints one line from the daemon's prompt cache file. Deliberately never touches the IPC socket (only reads a plain-text cache file the daemon maintains), so it's fast/safe enough to embed directly in `PS1`. Prints nothing if the cache is missing; prints `?` if the cache is stale (>300s old by default, overridable via `SHELLAGOTCHI_STALE_THRESHOLD_SECS`). |
| `shellagotchi status` | `--json` | Fetches live pet state from the daemon over IPC and prints a bordered ASCII status card (or, with `--json`, the raw `PetState` as pretty JSON). Unlike `feed`/`prompt`, this fails loudly (non-zero exit, clear stderr message) if the daemon is unreachable. |
| `shellagotchi show` | `--json` | Alias for `status` — identical behavior. |
| `shellagotchi watch` | — | Launches a live `ratatui` TUI showing the pet's sprite, mood, and stat gauges, polling the daemon in the background. Keybinds: `q` quit, `c` clean, `p` pet, `r` refresh. |
| `shellagotchi init <bash\|zsh\|fish>` | `--with-clean-alias` | Prints the shell integration snippet for the given shell to stdout (nothing else — meant to be piped straight into `eval`/`source`). `--with-clean-alias` additionally emits an explicit `clean()` wrapper function (bash/zsh only; ignored with a warning on fish, since fish's argv0-detection cleanup needs no wrapper). |
| `shellagotchi doctor` | — | Runs diagnostic checks (binary location, config parses, state dir writable, socket exists, daemon responds to ping, prompt cache present, rc-file hooks found) and prints a `[OK]`/`[FAIL]` report. Exits non-zero if any check fails. |
| `shellagotchi install` | — | Writes the systemd user unit file (`~/.config/systemd/user/shellagotchi.service`) and, if a systemd user session is available, enables + starts it. Never runs `loginctl enable-linger` automatically. |

Two additional hidden/internal subcommands exist purely for packaging
(not meant for interactive use, and not shown in `--help`):
`shellagotchi gen-man` (emits the `clap_mangen`-generated man page to
stdout) and `shellagotchi gen-completions <bash|zsh|fish>` (emits a
`clap_complete`-generated completion script to stdout). They're how
`man/shellagotchi.1` and `completions/shellagotchi.*` in this repo were
produced, and how you'd regenerate them after any CLI change.

### Man page and completions

A man page and shell completions, generated directly from the CLI
structure above (not hand-written, so they can't drift), are checked into
the repo:

```bash
man ./man/shellagotchi.1          # or install it into your MANPATH
source completions/shellagotchi.bash   # or completions/shellagotchi.zsh / .fish
```

Regenerate after any CLI change with:

```bash
cargo run -- gen-man > man/shellagotchi.1
cargo run -- gen-completions bash > completions/shellagotchi.bash
cargo run -- gen-completions zsh  > completions/shellagotchi.zsh
cargo run -- gen-completions fish > completions/shellagotchi.fish
```

## Config reference

Config lives at `~/.config/shellagotchi/config.toml` (override with
`SHELLAGOTCHI_CONFIG=<path>`) as TOML. Any keys you omit fall back to the
defaults below (partial files are fine — you only need to specify what
you want to change). Generated from `src/config.rs`'s `Config` struct and
its `Default` impl:

| Field | Default | Controls |
|---|---|---|
| `pet_name` | `"Pet"` | Display name shown in the status card, prompt, and TUI. |
| `boredom_after_minutes` | `45` | Minutes of no fed commands before boredom starts rising. |
| `max_feeds_per_min` | `30` | Reserved for future rate-limiting of feed events; not yet enforced by the engine. |
| `sleep_start_hour` | `23` | Hour-of-day (UTC, 0–23) the pet's nightly sleep window begins. |
| `wake_hour` | `7` | Hour-of-day (UTC, 0–23) the pet wakes up. Correctly handles windows crossing midnight. |
| `poop_interval_commands` | `40` | Pet poops once every N commands fed to it (a running counter, NOT time-based). |
| `unicode` | `true` | Whether rendering may use Unicode characters (vs. plain ASCII fallback). |
| `junk_food_commands` | `["rm", "kill", "pkill", "dd"]` | Argv0 values that always count as "junk food" (bump `bad_food_meter`) regardless of exit code. |
| `clean_commands` | `["clean", "shellagotchi-clean"]` | Argv0 values that trigger automatic pet cleanup (poops cleared, hygiene maxed) with no extra setup. |
| `ignored_exit_codes` | `[130]` | Exit codes (e.g. `130` = Ctrl-C/SIGINT) that are ignored entirely — neither a good nor bad meal. |
| `bad_food_meter_decay_per_hour` | `1` | How fast `bad_food_meter` decays back toward zero per hour of real time. |
| `max_offline_hours` | `12.0` (set `null`/omit for unlimited "hardcore mode") | Caps how many hours of elapsed real time a single catch-up tick will simulate, protecting against unrealistic decay after a long daemon-downtime gap. |
| `tick_interval_secs` | `60` | How often (seconds) the daemon's main loop ticks the pet forward on its own, independent of IPC requests. |

## FAQ

**Why is my pet dead, and how do I bring it back?**
Health reached 0 and its activity flipped to `Dead`. **Reviving/hatching a
new pet is not yet implemented** — the daemon's `Hatch` IPC op exists in
the wire protocol but its handler currently just returns
`"not implemented yet"` (see `src/daemon/ipc/server.rs`), and there's no
`shellagotchi hatch` CLI subcommand at all yet. `feed` still succeeds
silently against a dead pet (per its "never break the shell" contract),
but a dead pet's stats no longer meaningfully change. The current
workaround to start over: stop the daemon, delete
`~/.local/state/shellagotchi/pet.json`, and restart the daemon — it will
generate a fresh newborn pet. Genuine hatch/revive support is tracked as
future work.

**How do I disable it temporarily?**
Set `SHELLAGOTCHI_DISABLE` (to any value) in the environment before a
command runs, e.g. `SHELLAGOTCHI_DISABLE=1` in a shell session or exported
from an rc file conditionally. `shellagotchi feed` checks it first and
returns immediately without touching the daemon at all — no config
changes, no daemon restart needed. This is separate from stopping the
daemon itself (`systemctl --user stop shellagotchi` if installed via
`install`, or killing the `shellagotchi daemon` process directly), which
disables it more permanently.

**Does it survive my laptop suspending / the daemon being down for a
while?**
Yes — see `max_offline_hours` above. The next tick after the daemon comes
back simulates the elapsed time (capped), rather than either ignoring the
gap or applying an unbounded catastrophic decay.

**Why does `shellagotchi prompt` never seem to hang my shell?**
By design: it only ever reads a small plain-text cache file the daemon
maintains, never the IPC socket, so there's no connect/timeout latency on
your prompt's hot path, even if the daemon is completely gone.

## Performance

Measured on this development machine (`cargo build --release`, `strip =
true` in `[profile.release]`):

- Release binary size: **2.7 MB** (stripped via `strip = true` in
  `[profile.release]`), well under the plan's <8MB target.
- Daemon RSS after ~15s of running idle: **4.3 MB** (`VmRSS` from
  `/proc/<pid>/status`), well under the plan's <15MB target.

These are single-run sanity numbers from this environment, not a rigorous
benchmark; exact figures will vary by platform/allocator.

## Known gaps / future work

- `shellagotchi hatch` / pet revival after death is not implemented (see
  FAQ above).
- `max_feeds_per_min` is defined in config but not yet enforced by the
  engine.
- systemd's `sd-notify`/watchdog integration was considered in the design
  doc but dropped for simplicity — the shipped unit is a plain
  `Type=simple` service.
